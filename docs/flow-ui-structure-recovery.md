# Flow UI/UX 구조 개선 진단 및 단계별 정리안

작성: 2026-10-16 · 대상: `hoonex/blank-app` School / University Web

## 결론

새 UI 기능을 추가하는 방식에서 **기존 화면·스타일·데이터 흐름의 소유권을 명확히 하는 구조 개선**으로 전환한다. 전체 재작성(big-bang rewrite)이나 또 다른 마지막-우선 CSS 핫픽스 계층은 권장하지 않는다.

## 확인된 사실 (2026-10-16 main 기준)

- School 진입점 기준 루트 파일 패턴: `school*.js` **25개**, `school*.css` **14개**.
- 위 School CSS 파일에서 `!important` **1,449회** 발견. 이는 버그 개수가 아니라 우선순위 충돌 위험을 보여주는 구조 지표다.
- `index.html`은 기본 `school.css`, `school-v5.css`, `school-hotfix.css`, `school-polish.css`를 로드한다.
- `school-metrics.js`는 `school-ia.js`, `school-uiux-v2.js`, `school-today-topbar.js`, `school-runtime-contract-v6.js`, `school-real-device-hotfix.js`, `school-real-device-refine.js`, `school-final-visual-polish.js`, `school-desktop-tablet-redesign.js` 등을 단계적으로 불러온다.
- 일부 모듈은 런타임에 `<style>`을 주입한다. `school-metrics.js`는 특정 스타일 요소를 DOM 마지막으로 옮겨 CSS 우선순위를 다시 확보한다. `school-uiux-v2.js`는 여러 후속 CSS를 별도 로드한다.
- `school.js`는 프로필, API 요청/캐시, 날짜, 과목 편집, 화면 렌더링, 내비게이션까지 동시에 관리한다.
- School 대시보드 API는 시간표·급식·학사일정을 하나의 응답으로 반환하므로 브라우저에서 급식만 다른 TTL로 조회할 수 없다. 데이터 종류별 독립 TTL을 도입하려면 API 구조 변경이 선행돼야 한다.
- 현재 서비스 워커/Cloudflare 라우팅은 별도 계약에 의해 보호되며, 무심코 삭제/통합해서는 안 된다.

### 운영 화면 관찰 (실제 Flow URL, 테스트용 학교 프로필/급식 데이터)

- 390×844 모바일 / 1366×768 데스크톱에서 **가로 넘침 0px**, 화면 렌더링 정상 기동 확인.
- 두 환경 모두 실행 시 스타일시트 **39개**, 런타임 포함 `<style>` 요소 **27개**. 단순 파일 개수가 아니라 실제 화면에서의 누적 스타일 비용도 크다.
- 모바일 첫 화면은 상단 상태 카드 2개 아래에 7교시 전체 목록이 길게 펼쳐지고, 급식은 첫 화면 아래 끝부분에 제목만 나타난다. 하루에 확인할 핵심 정보의 우선순위보다 시간표 목록 길이가 우선한다.
- 데스크톱은 넓은 시간표 카드와 급식 카드가 나란하지만, 다가오는 시험 카드 하단은 첫 화면에서 잘린다. 모바일과 데스크톱의 정보 밀도·우선순위에 일관성 있는 규칙이 필요하다.
- 스크린샷은 일회성 검증 자료이며 실데이터 노출을 피하기 위해 테스트 데이터를 사용했다. 다른 화면·다크 모드·실기기 터치는 아직 별도 검증 대상이다.

## 제품 정보 구조 초안

**School**: 오늘(오늘 수업과 다음 수업, 급식, 가까운 일정) / 시간표·달력(주간·월간 조회 및 편집) / 학교 정보 / 설정. 대중교통은 제공 가능한 지역에서만 독립 기능으로 노출. 동일 기능이 홈 카드와 탭에 중복되어도 세부 편집·관리 기능의 정식 소유 화면은 하나로 둔다.

**University**: School과 같은 공통 셸(상단 정체성, 내비게이션, 디자인 토큰)을 쓰되 강의 시간표·캠퍼스·Everytime 공유 링크 기능은 도메인별로 분리한다. University 고유 기능을 School에 억지로 맞추지 않는다.

**반응형**: 휴대폰 바텀 내비게이션, 태블릿 화면 밀도, 데스크톱 사이드바의 목적지는 일관되게 유지한다. 901–1180px 및 회전 구간은 별도 기기 검증 대상이다.

## 권장 순서

### 0. 데이터 정책과 요청 경계 — 작은 변경, 낮은 위험

- 묶인 School 대시보드 응답의 로컬 캐시 유효기간을 12시간으로 변경한다.
- 날짜가 바뀌거나 새 날짜를 선택한 경우, 로컬에 데이터가 없거나 만료됐다면 갱신한다. 기존의 오늘 버튼 수동 강제 갱신을 유지한다.
- 탭이 열린 동안 30초 간격 시계 업데이트는 유지하지만 매 tick에 API를 호출하지 않는다.
- 교통 실시간 도착정보와 같은 고빈도 데이터는 대시보드 캐시와 공유하지 않는다.
- API가 데이터별 엔드포인트/수정 시각/ETag를 제공하게 되는 경우에만 급식·시간표·학사일정 캐시를 별도 분리한다.

### 1. 화면 소유권과 디자인 토큰 — 시각 기준선 확보 이후

- 폰트·색상·간격·경계·그림자·밀도·모션을 단일 tokens 레이어로 정의한다.
- 스타일 소유권을 Shell / Today / Timetable+Calendar / School / Settings / University로 구분한다.
- CSS 파일을 통째로 지우지 말고 실제 적용 스타일과 대응 테스트를 확인하며 한 컴포넌트씩 옮긴다.
- 이전 레이어를 대체하고 테스트에 성공한 뒤에만 기존 핫픽스를 삭제한다. 새로운 `!important`로 기존 레이어를 덮지 않는다.

### 2. 화면 구조 — 사용성 우선

- 오늘: 날짜/학교 맥락 → 다음 수업/오늘 시간표 → 급식 → 가까운 일정 순으로 1차 정보 흐름을 단순화한다.
- 시간표·달력: 날짜 이동, 과목 편집, 행사 확인의 동선을 하나의 일관된 화면으로 묶는다.
- 설정: 자주 쓰는 설정만 상단, 전문적인 설정은 그룹별 펼침으로 분리한다.
- 학교/대학교 모드의 헤더/내비게이션/공통 컨트롤을 재사용하되 도메인별 핵심 기능은 유지한다.

### 3. 상태·런타임 구조 — 중복 사이드이펙트 방지

- `school.js`에서 API/캐시, 날짜·프로필 상태, 뷰 렌더러, 과목 오버라이드 기능을 경계별 모듈로 단계적으로 분리한다.
- 뷰 렌더는 사용자 상태 변경에 의해 실행하며 뷰 전환만으로 원격 요청하지 않게 한다.
- 런타임 CSS 주입, Observer, 후순위 style 재배치 중 반드시 필요한 것을 확인하고 중복 계약을 순차 제거한다.
- 단일 이벤트는 단일 상태 갱신·필요한 뷰의 렌더에만 연결한다.

## 병합/출시 수용 기준

- 기능: 학교/반 설정, NEIS 급식·시간표·행사, 과목 오버라이드, University, 교통, PWA 오프라인이 유지될 것.
- 요청: 같은 학교·학년·반·날짜에 중복 대시보드 API 요청이 없을 것. 시계를 30초마다 갱신해도 유효 캐시는 네트워크 요청을 발생시키지 않을 것.
- 화면: 최소 390×844, 844×390, 768×1024, 960×1536, 1024×768, 1366×768, 1920×1080에서 overflow, 손가락 터치 영역, 1차 폴드와 카드 위계를 실제 스크린샷으로 확인할 것.
- 전환: 새 홈/학교/일정/설정 간 왕복과 새로고침에 상태가 유지될 것. 기존 CI를 통과할 것.
- 스타일: 새 UI 기능은 기존 컴포넌트의 소유 스타일을 편집한다. 새 패치 CSS 파일/관찰자/런타임 주입을 추가하지 않는다. 마이그레이션 후 파일·`!important` 감소량을 PR에 명시한다.

## 이번 변경의 범위

이 PR은 12시간 대시보드 캐시 정책과 이 구조 계획만 포함한다. 전체 UI를 한 번에 갈아엎거나 서버 API를 분할하지 않는다. 고품질 시각 리팩터링은 캡처 기준선·화면 우선순위를 정하고 별도 PR로 진행한다.
